Fix the tokenizer to preserve Nordic/extended-Latin letters by mapping ø→o, Ø→O, æ→ae, Æ→AE, å→a, Å→A, đ→d, Đ→D (and similar) BEFORE the non-Latin-script drop step. Add table tests for Højlund, Ødegaard, Haaland variants, Đoković-style names. Cross-check against the Man Utd + Arsenal + Barcelona + Bayern rosters for other affected surnames.

#### 1. FixtureReadyToComplete doesn't filter downstream-workflow check by e.removed — VAR-removed events with in-flight discovery hang fixtures forever
**Location**: `internal/infra/pg/fixture_repo.go:230-234`  
**Category**: correctness  

**Evidence:**

AND NOT EXISTS (
    SELECT 1 FROM event_downstream_workflows edw
    JOIN events e ON edw.event_id = e.id
    WHERE e.fixture_id = f.id
      AND edw.completed_at IS NULL
)

This clause joins event_downstream_workflows to events but never filters by e.removed = false. RegisterEventAbsence (event_repo.go:366-381) soft-deletes an event (removed=true, removed_reason='var') when its debounce counter hits 0, but nothing writes completed_at back into event_downstream_workflows for the still-running Discovery. MarkDownstreamComplete is only called by DiscoveryWorkflow's own final activity (discovery/activities.go:301-329) — which runs only if the workflow completes its 10-attempt loop naturally.

**Aug 14 impact:**

Real Aug 14 exposure. During a live match, a goal detected → 3 presence votes flip downstream_triggered=true → Discovery spawned with completed_at=NULL. If VAR reverses the goal mid-run AND anything (operator cancel, retention prune, worker restart) causes Discovery to exit without hitting MarkDownstreamComplete, the row stays completed_at=NULL forever. Fixture completion check never turns true. Fixture stays state='active' indefinitely, wasting Monitor cycles and holding up the completion event. Even without VAR, any orphaned event_downstream_workflows row from a crashed worker leaves the parent fixture stuck.

**Suggested action:**

Either (a) add `AND e.removed = false` to the second NOT EXISTS clause (treat removed events as 'no longer waiting for downstream'), or (b) extend RegisterEventAbsence to UPDATE event_downstream_workflows SET completed_at = NOW(), outcome_class = 'event_removed' WHERE event_id = $1 AND completed_at IS NULL in the same transaction. Option (b) preserves the audit trail; option (a) is simpler.

**Location**: `internal/infra/pg/fixture_repo.go:260-276`

#### 3. registerAndSpawnDiscovery silently swallows errors with no retry mechanism — orphans row or loses discovery
**Location**: `internal/activity/monitor/activities.go:674-702`  
**Category**: correctness  

**Evidence:**

```go
func (a *Activities) registerAndSpawnDiscovery(ctx context.Context, existing *event.Event, domainEv *event.Event, fixtureID int64) {
    if a.Spawner == nil { return }
    workflowID := fmt.Sprintf("discovery-%s", existing.ID)
    if err := a.EventRepo.RegisterDownstreamWorkflow(ctx, existing.ID, "discovery", workflowID); err != nil {
        // Non-fatal per Option B — log + continue. Skip the spawn to
        // avoid an untracked workflow; retry next cycle will re-attempt.
        return
    }
    ...
    if err := a.Spawner.SpawnDiscovery(ctx, workflowID, in); err != nil {
        // Non-fatal per Option B. The pending row exists; a follow-up
        // pass or manual intervention can spawn later.
        _ = err
    }
}
```
The comments claim 'retry next cycle will re-attempt', but this function is called ONLY when `justTriggered==true` in ReconcileFixture. RegisterEventPresence's pg impl gates the flip on `WHERE ... AND NOT downstream_triggered`, so `justTriggered=true` fires EXACTLY ONCE across the event's lifetime. Subsequent cycles see justTriggered=false and never re-enter this code path. There is no periodic recovery job.

FAILURE SCENARIO: Match day, Temporal server briefly unhealthy or pg connection blip. Event debounce hits count=3 for goal X. RegisterDownstreamWorkflow succeeds, SpawnDiscovery returns an error (e.g., transient DEADLINE_EXCEEDED from Temporal). Error is discarded via `_ = err`. Row in event_downstream_workflows has completed_at=NULL. All subsequent poll cycles skip this event (justTriggered stays false forever). Fixture reaches api_status=FT but FixtureReadyToComplete returns false because the orphaned row still shows a pending workflow. Fixture never transitions to completed. Alternatively: RegisterDownstreamWorkflow errors → no row → SpawnDiscovery skipped → FixtureReadyToComplete sees no pending row and completes fixture → SILENT VIDEO LOSS for that goal.

**Aug 14 impact:**

Two failure modes both plausible at production temporal/pg reliability: (A) silent video loss when RegisterDownstreamWorkflow errors and no row inserted; (B) fixture STUCK IN ACTIVE STATE indefinitely when row is inserted but SpawnDiscovery errors. Both are on-call debugging burdens on match day. Operator can manually SQL-patch, but only if they notice. This is worth catching before Aug 14.

**Suggested action:**

Return the error from registerAndSpawnDiscovery and let the ACTIVITY fail — Temporal retries the whole ReconcileFixture. Since RegisterEventPresence's vote insert is idempotent per (event_id, workflow_id), the retry re-enters with justTriggered=false; then add a repo method `IsDownstreamPending(event_id, workflow_type, workflow_id) bool` and re-invoke spawner if a pending row exists for this event. Alternatively: add a periodic recovery worker that reads event_downstream_workflows rows with completed_at=NULL older than N minutes and re-spawns them.

#### 4. seq counter breaks natural_key stability when VAR overturns an earlier goal by the same player
**Location**: `internal/activity/monitor/activities.go:452-495 (seqCounter build), internal/domain/event/event.go:187-193 (ComposeNaturalKey)`  
**Category**: correctness  

**Evidence:**

```go
// In ReconcileFixture:
seqCounter := make(map[string]int)
for _, apiEv := range in.APIFixture.Events {
    domainType := trackableType(apiEv)
    if domainType == "" { continue }
    seqKey := seqCounterKey(apiEv, domainType)   // team_player_type
    seqCounter[seqKey]++
    domainEv, key, err := a.buildDomainEvent(f, apiEv, domainType, seqCounter[seqKey], now)
```
And natural_key format:
```go
return fmt.Sprintf("%d_%s_%s_%d", teamID, pid, t, seq)
```
seqCounter is rebuilt from scratch every cycle from the CURRENT API events list — position-based, not identity-based. If an earlier event with the same (team, player, type) is removed from the API (VAR overturn), the seq numbers of subsequent SAME-KEY events SHIFT DOWN. Previously stored natural_keys become mismapped.

FAILURE SCENARIO: Player X scores at min 10, min 30, min 55 for team A (hat trick). All three insert as X_A_goal_1, X_A_goal_2, X_A_goal_3. After 3 cycles all three are downstream_triggered=true. VAR reviews min 10 → overturned → drops from API. Next cycle: API events = [X@30, X@55]. seqCounter builds X_A_goal=1 for min 30, X_A_goal=2 for min 55. Domain events computed with keys X_A_goal_1 and X_A_goal_2. pgByKey has X_A_goal_1 (min 10's row!), X_A_goal_2 (min 30's row!), X_A_goal_3 (min 55's row). The API's min 30 goal is mapped to min 10's pg row (RegisterEventPresence — downstream already triggered, no new discovery). The API's min 55 goal is mapped to min 30's pg row (same). min 55's row (X_A_goal_3) not in apiKeys → absence votes → count 3→2→1→0 → soft-removed. min 55 is a real goal but no new Discovery workflow is spawned for it as a distinct event.

**Aug 14 impact:**

Hat tricks + red cards from the same player are common in football (Premier League has hat tricks weekly). VAR overturns are increasingly common. When these coincide, the reconcile logic silently drops real goals from the discovery pipeline. Domain doc says 'Player refinement is handled by orchestration removing the old row + inserting a new one, NOT by mutating natural_key in place' — the current seq counter violates that principle. Real risk of missed goal videos on match days.

**Suggested action:**

Use a stable field (minute+extra, or the apiEv.ID if the vendor exposes one) as part of natural_key instead of a rebuilt-each-cycle seq counter. Or seed seq from a pg query counting existing NON-REMOVED events with this (team, player, type) prefix, not from the current API's list order. Ensures a goal's natural_key stays stable regardless of earlier goals' fate.

#### 5. SameSite attribute dropped on LoadCookies + ReplaceCookies — potential auth breakage
**Location**: `internal/twitter/browser.go:189-207 and 249-267`  
**Category**: correctness  

**Evidence:**

Both LoadCookies and ReplaceCookies build the OptionalCookie payload for AddCookies without copying `c.SameSite`. Round-trip: WriteBackup persists SameSite → ReadBackup returns SameSite → ReplaceCookies drops it before AddCookies. Playwright's OptionalCookie has a `SameSite *SameSiteAttribute` field, and its own type_helpers.go ToOptionalCookie explicitly copies `SameSite: c.SameSite` — this codebase omits it. **Aug 14 impact:**

Real. Twitter's session cookies (auth_token, ct0/csrf) are set with SameSite=Lax on the wire. Twitter may reject cross-origin form submissions or CSRF-protected endpoints because the cookies lack the required SameSite policy — surfacing as intermittent auth failures on match day after any cross-fleet cookie handoff.

**Suggested action:**

Add `SameSite: c.SameSite` (the *SameSiteAttribute pointer) when building OptionalCookie in both LoadCookies and ReplaceCookies. Guard against nil at read-side by writing a helper that converts a Cookie.SameSite string to the *SameSiteAttribute pointer via getSameSiteAttribute() only when non-empty.
