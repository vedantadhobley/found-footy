## Context

The 2026-08-15 cutover moved prod from Python (Mongo/MinIO) to Go (Postgres/Garage).
Two permission bugs bit during it — the non-root worker couldn't reach `docker.sock`
or write `/scratch` — both from a dev-runs-root / prod-runs-`app` (uid 1000)
divergence. This audit hunted that failure-class (dev/prod divergence, fresh-provision,
non-root fs/socket, runtime-vs-config, unbounded leaks, mutable-state correctness,
concurrency) before committing to the MLS test.

**Headline.** Every Tier-1 correctness gap and both resource-leak risks from the prior
audit ([audit-2026-08-05.md](./audit-2026-08-05.md)) were already closed. No finding
blocked the MLS test. The sharpest new findings were a silent cookie-write-back bug
(two stacked layers) and a per-process LLM cap that doubled joi's load under two worker
replicas — both fixed + deployed. The reset was done **in-place (no wipe)**: the fixes
are image/compose/code changes, and keeping the volumes sidestepped the entire
fresh-provision risk cluster.

## Findings by dimension

**1 · Deployment / runtime divergence.** The two cutover perm fixes are COMPLETE
(worker's only write path is `/scratch` ✓, only privileged socket is `docker.sock` ✓;
api writes nothing; fleet replicates seccomp/shm/mem/net; every service has `mem_limit`).
New: **[FIXED] cookie write-back EBUSY** (single-file bind mount → `rename(2)` EBUSY,
error swallowed → dir mount); **[FIXED] api `EVENT_ENV`** missing; MLS-253 league drift
in `.env.example` (**[FIXED]**; live `.env` was safe on the code default).

**2 · Fresh-provision.** **[FIXED]** Garage bootstrap was non-idempotent AND gated all
schedule creation (`s3.New` bucket-probe runs before `ensure*Schedule`) → scripted as
`garage-bootstrap.sh`. **[TRACKED]** `VerifySchema` validates a fingerprint, not object
existence — a crash mid-`initdb` could stamp a half-empty DB as OK (moot this reset: no
wipe, and the running worker already booted past the guard). Runbook: always `up --build`
(a stale `:latest` trips the drift guard).

**3 · Runtime-vs-config traps.** **[TRACKED]** `RetentionDays: 14` is a hardcoded literal
at `cmd/worker/main.go:390`, so `WORKFLOWS_RETENTION_DAYS` is dead config (config-blind +
create-only) — latent because live == 14; fix = pass the config value + make
`ensure*Schedule` reconcile (Update-on-drift). **[TRACKED]** resolved team aliases are
never re-resolved, so tokenizer/algorithm changes never reach the existing corpus — live
given ongoing tokenizer work. Schedules are create-only by design (tune via the Temporal
CLI); the reset's fresh schedules use current code. CLEAN: boot-cached config re-reads on
restart; schema drift guarded; S3/NATS/presign/namespace all clean.

**4 · Resource leaks.** **[TRACKED-P1]** `promote()` never `deleteStaging`s its Garage
staging object (every other terminal path does) → hundreds of GB/season, monotonic.
**[TRACKED-P1] #196 elevated:** an `EventWorkflow` that Closes without
`MarkDownstreamComplete` (30-min timeout / pg blip / panic) strands its fixture `active`
forever — the recovery re-spawn is `REJECT_DUPLICATE` so it can never re-drive — AND
pins the event's ~1 GB Firefox container; a few strandings on a busy day = memory
escalation. Fix: recovery `ALLOW_DUPLICATE_FAILED_ONLY` + an active-fixture max-age
force-complete backstop. **[TRACKED-P2]** `/scratch` never swept (OOM-restart orphans).
CLEAN: goroutines, connections/rows/bodies/readers, temp-file error paths, in-memory
growth (all per-execution/static), fleet reaper wired.

**5 · Mutable-state correctness.** **#199:** active-fixture refresh **[FIXED]**;
completed-fixture assist backfill **[TRACKED]** (monitor stops polling at completion;
API-Football fills the assister minutes-to-hours later). **[TRACKED-P2]** event
`player_name`/`team_name` + fixture league/round/kickoff aren't refreshed by the 30 s
monitor (ingest-owned, only today+future). **[DE-ESCALATED] #187:** three coexisting
`outcome_class` vocabularies, but it's dead-code/doc rot — no query reads
`event_downstream_workflows.outcome_class`, nothing user-visible. CLEAN:
score/status/elapsed/extra/winner/penalty refreshed every cycle.

**6 · Config parity + dead-code.** NO P0 config bug; the live prod path is clean (no
inline-comment poisoning, all compose `${VAR}` resolve). **[FIXED]** `.env.example` was
broadly stale (LLM pointed at nexus not joi — a fresh deploy would have failed; missing
`GARAGE_*` tokens the compose hard-requires; missing `EVENT_ENV`; MLS 253; dead
`DEPLOY_ENV`; missing fleet knobs; inline-comment examples). **[TRACKED-rot]** 8 dead
`scaler` comments + `ModuleMonitorWorkflow` dead const + ~16 stale `MonitorWorkflow`
comments + zero-caller funcs (`ffmpeg.Faststart`, `bootstrap.BlockUntilDone`, …) — sweep
pending.

**7 · Concurrency + idempotency.** **[FIXED]** the LLM semaphore is per-process, so at
`replicas: 2` it put up to 8 concurrent on a cap-4 joi → `cap=2`. **[TRACKED-P2]**
`AddPopularity` is a non-idempotent counter (soft vote; a Temporal retry double-applies).
**[TRACKED-P2]** permanent LLM errors (404/401/bad-JSON) are retried, not marked
non-retryable (bounded, not infinite). **[TRACKED-P2, latent]** fleet-cap and share-mint
TOCTOU (safe only while provisions are serialized). CLEAN: in-process LLM enforcement
airtight, fan-out error aggregation solid, 27 `ON CONFLICT` upserts, no unbounded retries.

## Cross-cutting (raise in dhobley/joi)

**LLM admission control belongs at joi**, not per-project client semaphores. A per-project
cap can't govern cross-project contention on the shared gateway — found-footy +
legal-tender + … each capping at 4 still sum to 4×N; only joi's `max_slots` enforces the
real global limit. The found-footy client cap is a documented STOPGAP (see
[decisions.md](../../decisions.md) 2026-08-15) until joi owns request queueing.
